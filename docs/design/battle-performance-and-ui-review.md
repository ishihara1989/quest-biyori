# 戦闘の引っかかりとUI便利機能の調査

2026-10-15の初期調査結果と改善候補。この文書の計測は変更前の記録。後続で適用した変更・追加の比較・未解決項目は[実装記録](../implementation/run-flow-and-performance.md)を参照する。

## 結論

最優先は敵撃破時の不要な能力再計算とUI再構築。終盤装備の雑魚周回で、1フレームの処理が最大 **1,186ms** になる場面を再現した。大量のスキル演出とは独立して起きる。

続いて、購入がなくても毎秒走る自動装備取得の全件検索と、Canvasの発光ぼかし・色調フィルター・大量のダメージ文字が重なる。戦闘計算そのものだけを別スレッドへ移す対応では、今回確認できた主要な負荷を解消できない。

## 計測条件と限界

- Windows / Ryzen 7 5800X / メモリ64GB。インストール済みChromeのheadless実行、1440×1000、Canvas 1024×576。CPU速度制限なし。
- 既存のエピックジェムUI検証用fixtureを再利用。6職Lv.100、全装備ノード、全アクティブLv.5、エピック12種装着。1倍速、自動装備ON、自動周回same。実プレイヤーの保存データではなく、終盤の負荷を調べるための構成。
- `epic`: 女神戦。敵HPだけを1e14にし、演出が十分に重なるまで継続。最大41分身・11契約・保留中の演出イベント2,353件。`farm`: 通常99ステージで実際に敵を倒して周回。
- 各条件は開始7秒後から実時間20秒を計測。仮想時計・早送りは使用しない。各比較で乱数の初期値を揃えるが、フレーム間隔や周回進行による多少の状態差は残る。
- 関数別計測とCPUサンプリングには計測負荷がある。値はこの環境の比較結果であり、実プレイヤー画面のFPSや停止原因を完全に断定するものではない。特にGPUの処理時間・画像デコード・実メモリ使用量は未測定。
- ブラウザからlocalhostへのHTTPアクセスが環境で拒否されたため、Playwrightのrouteで本編ファイルの実バイト列を返した。画像のデコード・描画は通常のブラウザ処理。ネットワークとHTTPキャッシュの性能は対象外。
- 比較で省いた処理は、隔離ブラウザ内の診断用差し替え。本編ファイル・素材は変更しない。UI更新を省く比較も正式な修正案の完成・検証ではない。

## 実測

「フレーム内処理」はゲームの描画コールバックを実行した時間。「フレーム間隔」は次のコールバックまでの時間で、描画・レイアウト・スケジューリングなども含む。両者の最大値は同じフレームとは限らない。20秒間のフレーム数は比較用で、ディスプレイへの実表示回数は保証しない。

| 条件 | フレーム数 | フレーム間隔 p95 / 最大 | フレーム内処理 中央値 / p99 / 最大 |
| --- | ---: | ---: | ---: |
| 女神・通常 | 627 | 50.0 / 66.6ms | 13.5 / 37.6 / 45.6ms |
| 女神・HUDと状態ツールチップ領域更新を省略 | 703 | 33.6 / 50.1ms | 11.7 / 32.7 / 38.9ms |
| 女神・shadowBlurのみ0 | 1,030 | 33.4 / 50.1ms | 12.4 / 32.9 / 43.5ms |
| 女神・Canvas filterのみnone | 792 | 33.4 / 50.2ms | 12.5 / 32.9 / 39.9ms |
| 女神・自動装備チェック省略 | 627 | 50.0 / 66.7ms | 13.1 / 23.9 / 36.7ms |
| 女神・ダメージと回復の文字描画を省略 | 727 | 33.4 / 50.1ms | 8.5 / 29.5 / 35.2ms |
| 99ステージ・通常 | 1,027 | 16.8 / **1,183.4ms** | 1.1 / 23.0 / **1,186.2ms** |
| 99ステージ・計測中のrefreshGrowthを省略 | 1,186 | 16.8 / 150.1ms | 1.0 / 19.4 / 68.1ms |

通常周回は普段の描画が軽いためp95だけでは停止を見落とす。最大値・長時間タスク・敵撃破との対応を見る必要がある。`farm`は7件の50ms以上のタスクを検出し、最長1,190ms。演出を維持したまま`refreshGrowth`だけを省く比較で大幅に軽減した。

関数別の時間は呼び出し先を含むため、表内の値を合計しない。

## 原因と改善順

### 1. 撃破のたびに全員分の能力と育成UIを再構築する【実測確認・最優先】

接続: [handleEvents / refreshGrowth](../../public/js/ui/forest-game.js)、[stats / effects / gearTree](../../public/js/core/forest-progression.js)。

`loot`イベント1件ごとに`refreshResources(); refreshGrowth();`を実行する。`refreshGrowth`は選択中の能力、6職のパーティ表示、全職のスキル表示を作るため、概ね12回の`P.stats()`を呼ぶ。`P.stats()`は毎回、武器・防具の全11ツリーを生成し直し、取得済みIDの配列を`includes`で何度も検索する。今回のfixtureは各部位1,041ノード、全員で12,492ノードを所持する。

周回計測では`refreshGrowth`27回が合計2,717ms、1回平均100.6ms、最大140.2ms。最悪のフレームでは、まとめて倒した敵の分だけ呼び出しが重なり、`refreshGrowth`が合計1,168msを占めた。うち`P.stats()`が1,131ms。大量のエフェクトがなくても約1秒止まる原因になる。

改善候補:

- 素材・ゴールド・新しい未装着ジェムの獲得では能力を変えないため、育成UIの再構築を外す。資源表示だけをイベント処理後に1回更新する。
- 育成表示はレベル・スキル・装備・装着ジェム・選択キャラが変わった時に更新する。自動装備が実際に購入した場合もここに含む。
- 装備ツリーの静的定義をキャッシュし、取得済みIDの集合を使う。能力値のキャッシュは状態変更時に確実に無効化する。
- 「1フレーム1回にまとめる」だけでは約100msの処理が残るため、不要な再計算の除去も必要。

### 2. 自動装備が購入0件でも毎秒全件を検索する【実測確認】

接続: [draw / runAutomaticGear](../../public/js/ui/forest-game.js)、[acquire](../../public/js/core/forest-auto-gear.js)。

ONの間は、資源・所持装備が変化しなくても毎秒12部位の候補を走査する。各ノードで取得済みID配列の`includes`を実行。全取得済みでも女神戦で平均20.0ms、最大25.3ms、20秒中20回。60Hzの1フレーム予算約16.7msをチェック単体で超える。省略比較では女神戦のフレーム内処理p99が37.6→23.9msになったが、描画フレーム総数は変わらず、描画側の負荷は残った。

改善候補は、資源・クリア・設定・所持装備の変更時だけ候補を更新し、所持判定をSet化、取得済み候補を除いたリストを維持すること。購入上限24件は1回の取得数の上限で、候補探索時間を抑える仕組みにはなっていない。未取得ノードが多い場合の探索・購入コストは別途確認が必要。

### 3. 発光ぼかし・色調フィルターと大量の透明画像の重ね描き【比較で影響確認】

接続: [忍者の分身・残像・弾](../../public/js/render/ninja-skill-renderer.js)、[巫女の大型演出](../../public/js/render/miko-skill-renderer.js)、[各職の描画](../../public/js/render/)。

分身は毎回`saturate / hue-rotate`と`shadowBlur`を付けて描く。多数の大きな透明素材や発光も同じCanvasに重なる。shadowBlurだけを0にした比較で20秒の描画フレーム数が627→1,030、filterだけをnoneにすると792に増えた。CPU内処理時間の変化だけでは説明できない差もあり、描画側を引き続き重点対象にする。GPU単体への帰属は未確定。

改善候補は、分身の色違いと発光を事前生成・キャッシュして通常画像として描くこと、同じ光・オーラの重複をまとめること、静的背景を合成済み画像にすること。派手さ・命中表現・敵の予告を残し、演出を消す比較をそのまま製品版には採用しない。キャッシュは全素材の全フレームを無制限に展開せず、現在必要な素材だけを保持する。

再描画・画像サイズのキャッシュとshadowBlur回避は[MDNのCanvas最適化](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)にも挙げられている。

### 4. ダメージ文字と全イベント配列の反復走査【実測確認】

女神戦20秒でダメージ17,143件、忍者演出15,000件。演出配列は最大2,353件。粒子は180個で上限があるが、ダメージ文字や演出イベント配列に同じ上限はない。複数の職別描画が毎フレームこの配列を先頭から走査し、ダメージは大半が`strokeText`と`fillText`の2回描き。描画時に一部演出を重複排除しても、元のイベント配列の大きさは減らない。

`drawEffects`は平均3.83ms、最大11.4ms。ダメージ・回復文字だけを省くと、フレーム内処理中央値13.5→8.5ms。戦闘のダメージ計算を減らす必要はない。表示だけを同一対象・同種別の50〜100ms程度で合算し、会心・大技を目立たせる候補が有力。職・種類別の描画キュー、実際の表示寿命に合わせた削除、表示数の予算管理も候補。数値合算時も実際のダメージ集計は正確に保つ。

### 5. HUD更新とスキルの並べ替え【実測確認】

[hud / refreshSkillCooldowns / syncCurseFocus](../../public/js/ui/forest-game.js)が毎フレーム動く。120個のスキル枠を毎回ソートし、比較のたびにIDをsplit、所有者をfind。表示しないスキル枠も対象。DOM移動は順序が変わった場合に限定済みだが、探索・ソート自体は毎回行う。

女神戦のHUDは平均1.53ms、うちクールダウン更新1.38ms。HUDと状態ツールチップ領域更新を省く比較でフレーム数627→703。クールダウン順・秒数表示を100〜200ms間隔にし、所有者参照とDOM参照を保持、状態が変わった部分だけ更新する候補。HP表示や操作の応答性は保つ。

### 6. 全地域の画像読み込みとメモリ圧迫【構造確認・停止との因果は未確定】

[起動時の素材ロード](../../public/js/ui/forest-game.js)は全地域の背景・敵・全職の全スキルを一括で読む。女神戦でPNG1,020件、圧縮ファイル合計約342MiB、元画像をRGBA4バイトで単純合計すると約2.20GiB相当。**ブラウザの実使用メモリが2.20GiBという測定ではない**。画像の参照保持、デコードキャッシュ、GPUへの転送などの追加調査が必要。

現在の地域・味方・直近の戦闘で必要な素材を読み込み、次の地域を先読みする案がある。女神の幻影が他地域の敵画像を使うため、単純に地域外の素材を除くと壊れる。資料館も展示対象単位の読み込みにできる。素材の縮小・余白削減は位置と全コマの検収が必要なので、まず読み込み範囲とキャッシュ寿命を整理する。

## 今回は主因と確認できなかったもの

- **保存**: 約274KiB、ジェム12個のfixtureでは周回時の`persist`が平均約1.2ms、最大1.5ms。1秒停止の主因は能力再計算だった。大量のジェムを溜めた実セーブ、保存領域の遅延・上限は未測定。
- **戦闘シミュレーション**: 女神戦の`update`は平均0.88ms、最大3.4ms。今回の構成では最優先の重い箇所ではない。敵・召喚数や2倍速による増大はあり得る。2倍速は今回未計測。
- **GC**: CPUプロファイルにGCはあるが、今回の長い停止は`refreshGrowth`で説明できる。無差別なオブジェクトプール化を先行しない。
- **非表示・メニュー中の再描画**: シミュレーションを止めても描画とHUDは継続する構造。メニュー・資料館の裏での再描画を抑える余地があるが、今回の戦闘中停止の比較対象にはしていない。

## UIの便利機能候補

既存の自動周回・自動装備・まとめて強化・ジェム保護・条件付き自動解体・一括解体・素材変換・未使用SP通知・資料館は確認済み。同じ機能を新規候補として重ねない。

| 優先 | 候補 | このゲームでの使い方・既存との差 | 規模 |
| --- | --- | --- | --- |
| 高 | 表示設定 | 演出品質、味方演出の不透明度、数値の合算、画面揺れON/OFF。現在はOSの動きを減らす設定への追従が中心。敵の危険予告と命中は常に見えるようにする | 中 |
| 高 | ジェムの検索・絞り込み | 効果・レア度・地域Lv・未装着・装着可能・保護で絞る。任意の効果量や必要容量でソート。現状の装着中優先・レア度・Lvの固定ソートを拡張 | 小〜中 |
| 高 | セーブ書き出し・読み込み | ファイルでバックアップ、読込前の進行と日時のプレビュー。現状はlocalStorageとリセット。長時間育成の安心につながる | 中 |
| 中〜高 | 周回セッションの集計 | 開始からの時間、クリア/敗北数、素材・ゴールド/時、平均・最速クリア、職別ダメージ/回復/被害。今ある1戦ごとのリザルトに追加。イベント全履歴は保持せずカウンターで集計 | 中 |
| 中 | スキル・ジェムのプリセット | 雑魚周回/ボス/素材用などを保存し、パーティ単位で切替。所持・容量・SPを再検証し、未所持・他キャラ使用中の扱いを明示。ジェム説明文は増やさず効果名と数値を維持 | 中〜大 |
| 中 | 素材の入手先へのショートカット | 強化・制作の不足素材をクリックして、解放済み入手先のステージ選択へ移動。未発見情報を明かさない。選択と戦闘開始は既存の操作に合わせる | 小〜中 |
| 中 | 周回の終了条件 | 次の1回で停止、N回、目的素材N個、全滅で停止など。現状の同じ/次へ/OFFを拡張。ボタンと小さな状態バッジ、詳細はツールチップ | 中 |
| 後段 | 離席中の進行と復帰サマリー | 現状はdocument.hiddenで戦闘進行を止める。最小化・別タブ・オフラインを含めて進行ルールを設計し、復帰時に獲得分を表示。経済・保存・時間上限に作用するためUIだけの変更ではない | 大 |

他作品の例としてMelvor Idleにはセーブのexport/import機能がある（[公式Wikiの更新履歴](https://wiki.melvoridle.com/w/V1.0.1)）。上の優先順位は本プロジェクトの実装と操作から判断した提案で、各作品の機能を網羅した市場調査ではない。

## 推奨する着手順と確認

1. 撃破時の育成再描画を外す。資源更新をまとめ、静的ツリー・所持判定を軽くする。
2. 自動装備を変更検知に寄せる。買えない・全取得済みの状態で同じ検索を繰り返さない。
3. ダメージ文字の合算、発光・分身色の事前処理、HUDの更新間隔を調整する。
4. 表示設定・ジェム検索・セーブバックアップを追加する。
5. 画像ロード範囲とメモリ、周回集計・プリセットを進める。

最適化時には、この2種の戦闘に加え、変更箇所の接続を確認する。能力キャッシュなら装備購入・レベル上昇・スキル振替・ジェム付替え・読込・自動装備を、描画なら通常/高密度/一時停止/メニュー/地域切替を対象にする。戦闘式を変えない最適化で全地域の30配置計算を自動的に繰り返さない。素材や共通描画を変える場合は[テスト方針](../policies/testing-policy.md)に従って全コマ・連続再生と利用元への確認を選ぶ。

## 再現ツールと記録

[性能調査ツール](../../tools/verify/profile-battle.cjs)を追加。`output/battle-profile/`に生のフレーム時間、関数別集計、Chrome CPUプロファイル、スクリーンショットを保存する。後半に実行した条件では要求画像の一覧と元画像RGBA換算量も保存する。初期の条件のResource Timingは標準バッファ上限で欠けているため、画像件数の根拠には使用していない。ブラウザエラーで失敗した診断条件は修正後に再実行し、成功結果で置き換えた。

```sh
npm run profile:battle -- --seconds=20 --cases=epic,farm
# 診断用の比較（製品版の変更ではない）
npm run profile:battle -- --seconds=20 --cases=epic-no-hud,epic-no-blur,epic-no-filter,epic-no-auto,epic-no-text,farm-no-growth
# 追加調査が必要なときだけ実行
npm run profile:battle -- --seconds=20 --cases=epic --speed=2 --trace
```

全8条件は実行エラーなし・ダメージイベントありで計測完了。素材や本編の変更がないため、戦闘バランス・素材の再検収は今回の対象外。成功済み条件は報告書作成のためには再実行していない。
