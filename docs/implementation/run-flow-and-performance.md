# クリア時の報酬・戦闘中の育成・ジェム整理と性能改善

2026-10-15の追加指示を適用。[初期の性能調査](../design/battle-performance-and-ui-review.md)の後続記録。

## 報酬と周回

- 素材・ジェム・撃破ゴールドは、敵を倒した時点では所持品へ入れず、クリア時にまとめて付与する。敗北・途中のステージ変更・再読込ではその周の未受取分を失う。未受取分は保存しない。
- 戦闘中は敵種ごとの撃破数、ゴールド、端数だけを保持。クリア時に各敵の従来の素材・ジェム抽選を実行し、ジェムの自動解体もこの時点で処理する。敵ごとの確率・確定分・トレハン・特殊ステージのドロップLvと倍率は変更しない。
- ゴールド端数は勝利時に撃破分→クリア報酬の順で引き継ぐ。敗北・中断時は、その周の開始前の端数を維持する。所持品から使った育成費用や回復薬は戻らない。
- 同じ周の報酬を二重に受け取れない。リザルトに表示するジェム・破片・ゴールドは実際に付与されたものに一致する。
- 抽選をクリア時に移したため、旧版と同じ乱数の種でも、個別のドロップや戦闘の乱数列までの一致は保証しない。基本確率での各敵の分布は維持している。2026-10-16にジェムの合計100%上限を撤廃し、レア度ごとの確定個数＋端数抽選による複数個を全件受け取るよう修正。

## 戦闘中の育成とリザルト

- 装備強化・スキル・ジェム・資料館などのメニューを開いても戦闘は進む。手動の一時停止と非表示タブでの停止は維持する。
- 自動周回が進んでも操作中のメニューを閉じない。クリア報酬と育成状況が更新された場合は、選択・フォーカス・スクロール位置をできるだけ保って内容を更新する。
- 能力・スキルパラメータは戦闘開始時に計算して使い続ける。育成結果は保存し、次の周・再挑戦・別ステージの開始時に反映する。本編UIから実行中のrunに`applyBuilds`を呼ばない。
- 育成画面は保存済みの育成結果を表示し、戦闘中は「次の周に反映」を表示する。育成画面のHP/MPは育成後の最大値、戦闘側のHP/MP・能力・スキル枠は実行中の能力に揃える。
- 初クリアで仲間が増えた場合も、実際に戦闘へ参加するのは次の開始から。加入・機能解放の演出は維持する。
- リザルトにステージ選択を追加。リザルトから開いたメニューでは、自動周回の待ち時間を止める。閉じると待ち時間を再開し、ステージ開始を選ぶとそのステージへ進む。

## ジェム画面

装着済みを全員・両部位の混在リストで並べる表示をやめ、次の区画に分けた。

1. 選択キャラの選択部位（武器／防具）の装着済みジェム。
2. 未装着ジェム。
3. 折りたたみ可能な「ほかの装備」。キャラ・部位ごとの見出しを付ける。

未装着欄に名前・効果の検索、レア度・地域Lv・効果・装着可能・保護のフィルターを追加。レア度・地域Lv・入手順・必要容量・選択効果の数値を昇順／降順で並べ替えられる。「条件解除」で戻せる。装着可能の判定は職業・専用部位・残りの各方向／共通／専用容量まで確認する。絞り込んでも現在の装着欄は隠さない。

検索中のフォーカスとカーソル位置を維持し、検索入力のblur/changeによる再描画の再入を防止した。リザルト・制作・解体候補からジェムを見る時は、残っている絞り込みを解除して対象を表示する。効果説明は既存の効果名・数値を維持した。

長いメニューをスクロールしても見出し・閉じるボタンは上部に固定する。ジェム画面にも「次の周に反映」を表示する。

## 性能改善

| 対象 | 適用した変更 |
| --- | --- |
| 敵撃破 | 所持品更新・能力再計算・育成UI再構築・保存を毎回行わず、撃破数などの加算に限定 |
| 能力計算 | 装備の静的定義をキャッシュ。取得済みIDはSetで判定。育成結果の計算は変更時に無効化するキャッシュを使い、戦闘用の開始時能力と分ける |
| 強化画面 | 各ノードの一括取得経路で、毎回全地域のツリーを生成しない。返す経路ノードはコピーし、呼出元の変更が定義へ漏れないようにする |
| 自動装備 | 資源・クリア・設定・育成などが変わった時だけ検索。所持・クリア判定はSet化。2026-10-22に24件／秒の制限を撤廃し、約4msを目安に探索・購入を中断して次フレームに継続。優先順位と前提別の待機リストで全候補の反復走査を削減。[現在の仕様](auto-gear-and-unlocks.md) |
| スキルの再使用表示 | 100ms間隔で並べ替え・秒数を更新。所有者・スキルIDを保持し、ソート比較のたびのsplit/findをやめる |
| ダメージ文字 | 同じ対象・発生元・種別・会心・スキル区分の100ms内の数値を表示上だけ合算。ダメージ計算・報酬・戦闘イベントの量は変えない |
| 忍者の分身 | 同じコマの色加工・発光をCanvasにキャッシュし再利用。半透明と向きを保つ。LRUで最大24MiBに制限 |
| リザルト | 最初の700msは撃破モーションを進め、その後の戦闘Canvasは最後の画像を再利用。リザルトの演出と周回タイマーは進む |
| メニュー・リザルト背景 | 画面全体のbackdropぼかしを外し、暗幕で読みやすさを保つ。戦闘スキルの光・粒子・残像は維持 |

### 計測結果

初期調査と同じ終盤fixture、Chrome 155 headless、1440×1000、1倍速、開始7秒後から実時間20秒。CPU計測の負荷を含む比較で、実プレイヤー画面のFPSを保証する値ではない。各関数の時間は呼び出し先込み。

| 指標 | 変更前 | 最適化後 |
| --- | ---: | ---: |
| 99ステージ周回のフレーム内処理・最大 | 1,186.2ms | 19.7ms |
| 女神・全エピックのフレーム内処理・中央値 | 13.5ms | 7.5ms |
| 女神・全エピックのフレーム内処理・p99 | 37.6ms | 11.9ms |
| 女神・全エピックの20秒間の描画コールバック数 | 627 | 916 |
| 女神・HUDの平均処理時間 | 1.53ms | 0.19ms |

女神戦は最大41分身・11契約を維持。表示待ちの演出配列は最大2,353→1,261件。色・発光キャッシュは約27,000回使われ、呼出し平均約0.002ms。自動装備の全取得済みチェックは、状態が変わらない戦闘中には走らなくなった。

周回のJavaScript由来の約1秒停止は再現しなくなった。一方で、最適化後も周回計測に最大約117ms、女神戦に最大約67msの**描画コールバック間隔**が残った。これはフレーム内処理時間とは別の指標。追加トレースでは戦闘終了後の150ms間隔にGPUタスクが重なり、同じ区間のゲーム処理は約1msだった。背景のぼかしと終了後の再描画を減らしても、全ての画面合成の遅延まで解消できたとは判断していない。

性能記録は`output/battle-profile/summary.json`。変更前の`farm`/`epic`、最適化後の`optimized-farm`/`optimized-epic`、終了画面をさらに調整した`final-farm`、追加調査の`trace-optimized-farm`を保存。初期調査の成功済みの8条件を報告書のために繰り返していない。

## 検証

- 報酬：途中撃破では付与・能力再計算なし、クリア時だけ付与、二重受取防止、敗北・中断で破棄、トレハンの確定分、特殊ステージのLvと倍率、自動解体。
- 能力：装備・スキル・ジェムの変更後も実行中の能力は変わらず、次の開始で反映。全6職・全10地域と女神の装備効果を定義からの集計と比較。購入・リセット・別セーブでキャッシュが混ざらない。
- ジェム：キャラ／部位別の区分、複合検索、各種ソート、保護と装着可否、通常幅・390px幅、検索再描画とフォーカス。
- 本編：メニュー中の戦闘、一時停止、自動周回でメニュー保持、リザルトからステージ選択、敗北時の報酬0、育成後の再読込、序盤の初回クリア・仲間加入。
- 分身：通常描画とキャッシュ描画を、半透明2種類・左右両向きで画素比較。最大差3/255以下・平均差0.2/255未満。全エピック戦でも継続描画と実行エラーなしを確認。
- ドロップ率・成長式・戦闘式・素材フレーム自体は変更していないため、全地域の30配置のバランス計算と未変更素材の全コマ検収は繰り返していない。変更した処理の利用元・状態変更・見た目に確認を絞った。

```sh
npm run test:run-flow
npm run check:run-flow-ui
npm run check:run-flow-ui -- --full-motion
npm run profile:battle -- --seconds=20 --cases=farm,epic --label=optimized
npm run check:structure
```

追加の共通処理回帰は、育成・ジェム・エピック・自動装備・装備外観・素材変換・戦闘基本動作・本編定義・発見制御・報酬を含む139テストが合格。ブラウザは通常演出・動きを減らす設定の両方で確認した。

## 次の課題

- 画面合成側の短い停止と、大量の透明エフェクトの重なりを引き続き切り分ける。今回の変更で完全な60fpsを保証しない。
- 全地域の画像の一括読み込みは残っている。地域単位の読込・先読み・キャッシュ解放には、女神の幻影と資料館の参照も含めた確認が必要。
- 表示品質の切替、セーブのバックアップ、周回セッション集計、育成プリセットは未実装の候補として残す。オフライン進行は報酬経済と保存仕様を含む別の設計が必要。
