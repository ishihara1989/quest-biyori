# ワークツリーを使う開発手順

2026-10-16制定。開発者1人で運用し、ローカルの `main` を確認済みの基準、GitHubを主にバックアップとして使う。

## 転生関連の継続開発

2026-10-20のユーザー指示により、転生関連の開発は今後も **ローカルの `dev` を開始元・統合先** とする。転生に関わる機能・UI・素材制作に適用する継続ルールであり、一般の変更で使う `main` 起点・統合先の例外とする。

1. ローカルの `dev` を明示して `codex/<作業名>` の作業ブランチと別ワークツリーを用意する。同じ作業のワークツリーがあればそこで続ける。
2. 作業用ワークツリーで実装・必要な検証・コミットまで進め、結果を報告して明示的なマージ指示を待つ。
3. マージ指示後は、必要に応じて最新のローカル `dev` を作業ブランチへ取り込み、統合結果を確認して `dev` へ `--no-ff` でマージする。
4. 統合した `dev` を `git push origin dev` でバックアップする。ローカルのみの指示がある場合は従う。
5. Git管理外の原画・検収画像を保全してから、終了したワークツリーを整理する。

以下の手順にある開始元・統合先・バックアップ先の `main` は、転生関連の作業では `dev` と読み替える。Cloudflare公開は引き続き別途指示を受ける。

## 基本の流れ

1. ローカルの `main` から作業用ブランチと別ワークツリーを用意する。
2. 作業用ワークツリーで実装・検証し、確認対象をコミットする。
3. 変更内容・検証結果・確認方法を報告し、ワークツリーを残して待つ。
4. ユーザーが明示的にマージを指示したら、確認した変更を `main` にマージする。
5. 統合した `main` を `origin` に通常pushし、バックアップを更新する。
6. 必要な制作画像と記録を保全してから、終了したワークツリーを整理する。

PR・GitHub上のレビュー・developブランチは必須にしない。通常の開発依頼は作業ブランチでの実装・検証・コミットまでを含む。「確認して」「よさそう」だけではマージ指示と解釈しない。「mainにマージ」「mainへ反映」など、統合先と操作が明確な指示を待つ。`main` の直接編集はユーザーがその例外を指定した場合に限る。

マージ指示には、その後のGitHubへのバックアップpushまでを含める。ローカルだけに留める指示があれば従う。Cloudflareへの公開は別の指示で行い、バックアップpushで自動公開する設定には変更しない。

## 作業開始

最初に現在のブランチ、未コミット変更、既存ワークツリーを確認する。同じ作業のワークツリーがあればそこで続ける。新しい作業は `codex/<短い作業名>` のブランチに分ける。別の作業の未コミット変更を移動・破棄・混入させない。

開始元には **ローカルの `main`** を明示する。GitHubへのバックアップが遅れていても、手元の統合済み変更を取りこぼさないため。リモートのデフォルトブランチや現在開いている別の作業ブランチから、暗黙に作り始めない。管理されたワークツリーがdetached HEADで作成された場合は、編集前に作業ブランチを作る。

通常のGitで作成する例（基準のリポジトリで実行。`example` は実際の作業名に置き換える）：

```powershell
git status --short --branch
git worktree list
git worktree add -b codex/example ../idle_rpg_poc-worktrees/example main
cd ../idle_rpg_poc-worktrees/example
git lfs checkout
```

ワークツリーは本編・制作データのディレクトリ内へ入れない。作業開始時にワークツリーの絶対パス、作業ブランチ、開始元のコミットを把握する。`main` を開いている基準フォルダは、確認済みの状態を維持する。

## LFS・依存関係・ローカル制作画像

ワークツリーはGit履歴とLFSストレージを共有するが、作業中のファイル・`node_modules/`・Git管理外の画像は別になる。

- 本編画像がLFSポインタのままなら、まず作業用ワークツリーで `git lfs checkout` を実行し、ローカルにあるLFS実体を展開する。実体が不足する場合に `git lfs pull` で取得する。
- npm依存が必要な作業では、そのワークツリーで `npm ci` を実行する。文書編集・構造検査だけの作業には不要。
- 原画や検収GIFが必要なら、基準フォルダやバックアップから必要なものだけを、作業用ワークツリーの同じ相対パスへコピーする。
- 基準フォルダの制作画像を直接書き換えない。編集する素材の共有に、ジャンクションやハードリンクを使わない。
- 新しく制作した原画・検収画像はGitのマージでは移らない。終了前に必要なものを基準フォルダの `development/` の同じ相対パスへコピーするか、別のローカルバックアップに保全する。既存ファイルと異なる内容が衝突した場合は、版を分けて保持し、勝手に上書きしない。
- 本編に採用する画像は作業ブランチの `public/assets/` に登録してLFSでコミットする。プロンプト・レシピ・生成記録もGitに保存する。GitHubだけでは管理外の原画を復元できない。

保全する制作データの配置は [リポジトリの配置基準](repository-structure.md)、LFSの復元や公開手順は [GitHub・LFS・Cloudflareの運用](../production/github-lfs-and-cloudflare.md) に従う。

## 実装と検証

変更した機能と接続部分を [テストと動作確認の方針](testing-policy.md) に従って確認する。構造・文書リンクを変更した場合は `npm run check:structure` を実行する。毎回の全テスト・全地域監査・素材再生成は必須にしない。必要な確認が通り、新しい変更や懸念がなければ同じ検証を繰り返さない。

ブラウザ確認用サーバーは、作業用ワークツリーをカレントディレクトリにして起動する。基準フォルダと同時に起動する場合は、未使用のポートを選ぶ。

```powershell
$env:PORT = '4192'
npm start
```

確認URLにはそのポートを使い、起動元のワークツリーとブランチを報告する。ポートが違えばlocalStorageも別になるため、作業確認用のセーブを使える。実際のプレイヤーのセーブをテスト入力として書き換えない。ポート競合時に別の作業のサーバーを勝手に停止しない。

## 確認待ちにする状態

変更内容を確認し、今回の作業に属するファイルだけをステージして、意味のある単位でコミットする。画像を無理に追加する `git add -f` や、未確認の一括追加は避ける。確認対象の追跡ファイルに未コミット変更を残さない。

完了報告には次を含める。

- 変更内容と、ユーザーが確認する操作・URL。
- ワークツリーの絶対パス、作業ブランチ、確認対象のコミット。
- 実施した検証と結果。未実施・未合格の必須確認や制約があればその内容。
- `main` へのマージ待ちであること。

確認待ちでは作業ブランチとワークツリーを保持する。マージ、基準フォルダへの追跡ファイルのコピー、Cloudflare公開を先行しない。途中の作業ブランチをGitHubへ保存したい場合は、バックアップの指示を受けてそのブランチだけをpushする。GitHubでのPR作成は要求がある場合に行う。

## マージの指示を受けた後

1. 指示対象のブランチ・コミットを確認する。作業用と `main` 用のワークツリーがともにクリーンであることを確認し、未コミット変更を巻き込まない。
2. 確認後に `main` が進んでいれば、まず作業ブランチへ最新のローカル `main` をマージする。競合を解消し、新たに影響する接続部分を検証する。仕様判断が必要な競合はユーザーに確認する。
3. `main` 用のワークツリーで作業ブランチを `--no-ff` でマージする。作業単位をマージコミットとして残す。確認済みのコミットを含むことと、統合結果が検証した内容と一致することを確認する。
4. `git push origin main` でGitHubのバックアップを更新する。通常pushが拒否されたら原因を調べ、force pushで置き換えない。push失敗時は、ローカルのマージは完了したこととバックアップ未更新を区別して報告する。
5. マージコミット、バックアップ結果、制作データの保全・ワークツリーの扱いを報告する。

例（ユーザーからマージ指示を受け、上記確認が済んだ後、`main` 用のワークツリーで実行）：

```powershell
git status --short --branch
git merge --no-ff codex/example -m "Merge codex/example"
git push origin main
```

`main` の統合結果が検証した作業ブランチと同じなら、報告のためだけに全検証を再実行しない。古い `master` はGitHub管理開始前の復旧用履歴なので、開発やマージの開始元に使わない。`--all`・`--mirror` による一括pushは使わない。

## 作業終了後の整理

マージとバックアップが済み、必要な管理外データを保全してから、その作業のサーバーを停止し、終了したワークツリーを削除またはアーカイブする。管理されたワークツリーは対応するアーカイブ操作で整理する。アーカイブが管理外の画像を保存するとは限らないため、原画などの保全を先に行う。

マージ済みのローカル作業ブランチは、保持が不要なら通常の削除（`git branch -d`）で整理する。マージ待ち、push失敗、制作画像の保全未完了の作業は保持する。未追跡データを巻き込む強制削除や `git clean -fdx` は使わない。
